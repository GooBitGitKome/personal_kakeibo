# Personal Kakeibo 開発仕様書

Version: 2.1 Draft  
基準: 利用者提供のソフトウェア設計仕様書 v2.0およびAI Coding Agent Development Policy  
対象: iOS・iPadOSの個人用家計簿  
状態: 初回版のコード実装とMacでの15件のテストを実施。署名・iCloud同期・実機UI検証は未実施。詳細は[検証記録](validation.md)を参照。

日常の収支を少ない操作で記録し、同じApple AccountのiPhoneとiPadで継続利用できるアプリを開発する。MVPは入力、履歴、集計、カテゴリ、月間予算、iCloud同期、CSV出力、JSONバックアップと復元を提供する。

元仕様のチェック済み項目は新規プロジェクトの実績として引き継がない。ここで「必須」とする事項は元仕様の要件であり、「提案」とする具体化は開発者レビュー後に採用する。提案のうちデータ互換性や利用者データに影響するものは、未決定のまま実装しない。

## 1 対象と制約

### MVPに含める機能

- 円建ての収入・支出を手入力する。
- 取引を月別に表示し、カテゴリで絞り込み、編集・削除する。
- 月間収入・支出・収支、カテゴリ別支出、月別推移を表示する。
- カテゴリの追加・名称変更・並べ替え・アーカイブを行う。
- 月間予算を設定し、使用額・残額・使用率を表示する。
- SwiftDataで端末内に保存し、CloudKit Private Databaseで同期する。
- CSVで取引を出力し、JSONでカテゴリ・予算を含むバックアップと復元を行う。
- iPhone・iPad、VoiceOver、Dynamic Typeに対応する。

### MVPに含めない機能

Web・Android、独自サーバー、独自会員登録、広告、課金、外部解析SDK、銀行・カード明細連携、AI家計アドバイス、家族共有は対象外。カメラ・OCRはMVP後とし、未使用のスキャナークラスは先に作成しない。

### 開発環境の提案

iOS・iPadOS 17以上を最低対応版の候補とする。SwiftUI、SwiftData、Swift ChartsとApple標準フレームワークを使用する。採用Xcode・SwiftバージョンはMacでビルド検証して固定する。LinuxではiOSビルド・実機同期を検証できない。

## 2 アーキテクチャ

```text
SwiftUI View → ViewModel → Use Case → Repository Protocol
                                          ↑ 実装
                                  SwiftData Repository
                                          ↓
                                      SwiftData
                                          ↓
                                 CloudKit Private Database
```

| 層 | 責務 | 禁止する依存 |
| --- | --- | --- |
| Presentation | 画面、入力状態、確認ダイアログ、結果表示 | ViewからModelContextを操作しない |
| Application | 作成・更新・削除・検索・復元の調整 | SwiftUIに依存しない |
| Domain | 値モデル、入力規則、金額計算、Repositoryの契約 | SwiftData、CloudKitに依存しない |
| Infrastructure | 永続化、Mapper、ファイル形式、同期変更の受信 | UIの状態を直接変更しない |
| App | 依存の組み立て、ModelContainerの初期化 | ビジネスルールを置かない |

単一アプリのモジュラーモノリスとする。Domainは値型、永続化は@Modelクラスとし、Repository内で変換する案を採用候補とする。RepositoryプロトコルはDomainに置く。処理件数が少ないMVPではMainActor上のModelContextを基本案とし、大量復元の処理方式は負荷試験で判断する。

同期由来の変更をInfrastructureから変更通知としてApplicationへ渡し、ViewModelは再取得して画面を更新する。アプリがactiveになった際にも再取得する。具体的な通知機構はSwiftDataの採用SDKで検証し、画面更新のために定期同期通信を独自実装しない。

## 3 データモデル

### Transaction

| 属性 | 型 | 規則 |
| --- | --- | --- |
| id | UUID | 論理ID、作成後は変更しない |
| typeRaw | String | incomeまたはexpense |
| amount | Int64 | 1以上、円単位 |
| categoryId | UUID | 存在する同じ収支区分のカテゴリを参照 |
| occurredAt | Date | 取引日時 |
| memo | String | 未入力は空文字 |
| sourceRaw | String | manualまたはreceipt。MVPの新規入力はmanual |
| createdAt | Date | 作成日時、更新時に保持 |
| updatedAt | Date | 更新時に変更 |

### Category

| 属性 | 型 | 規則 |
| --- | --- | --- |
| id | UUID | 論理ID |
| name | String | 空白だけの名前を拒否 |
| typeRaw | String | incomeまたはexpense |
| sortOrder | Int | 表示順 |
| isArchived | Bool | 新規入力の選択肢から除外する |
| createdAt | Date | 作成日時 |
| updatedAt | Date | 更新日時 |

初期支出カテゴリは食費、日用品、交通費、住居費、医療費、娯楽費、その他。初期収入カテゴリは「給与」「その他」を提案する。

アーカイブしても履歴の参照を維持する。名称変更は過去の表示にも反映する。提案としてカテゴリ区分は作成後変更不可とし、アーカイブ解除を提供する。編集中の取引がすでにアーカイブ済みカテゴリを参照する場合、同じ区分のままそのカテゴリを保持できる。別カテゴリへの変更先には有効カテゴリだけを提示する。

初期カテゴリは固定の論理UUIDを用いる案とする。ただし固定UUIDはCloudKit上の物理レコード重複を防がない。同一論理IDを検出した場合、updatedAt順の表示上の統合と、不一致内容の扱いをレビューする。重複レコードを無断で物理削除しない。

### Budget

| 属性 | 型 | 規則 |
| --- | --- | --- |
| id | UUID | 論理ID |
| monthKey | String | YYYY-MM、実在する年月 |
| amount | Int64 | 月間予算、円単位 |
| createdAt | Date | 作成日時 |
| updatedAt | Date | 更新日時 |

提案として設定する予算は1以上とし、未設定はBudgetが存在しない状態で表す。月に対する論理的な予算は1つとする。同期で複数レコードが生じた場合は検出し、updatedAtの新しい値を表示する案をレビューする。日時が同じ場合の比較規則も固定し、同期前の一意性を保証しない。

## 4 入力と計算

### 金額と入力検証

金額の保存・加減算にFloat・Doubleを使用しない。入力文字列は数字列として検証し、Int64への変換失敗を入力エラーとする。ゼロ、負数、小数、範囲外、存在しないカテゴリ、区分不一致を保存しない。

集計はオーバーフローを検出する。オーバーフロー時は明示的な集計エラーを表示し、切り捨てやゼロ表示をしない。チャート描画座標や使用率に必要な浮動小数点変換は、検証済みの整数から表示のためだけに行う。

提案: メモ上限1,000文字、カテゴリ名上限40文字。未来日を許可する。保存後は金額とメモを空にし、区分・カテゴリ・日付を保持する。制限値はレビューで確定する。

### 年月と日付の提案

グレゴリオ暦とAsia/Tokyoを月の集計基準にする。取引日時はDate、月間予算は年月文字列で保存する。月の検索範囲は月初以上・翌月初未満とし、端末間で同じ結果を得る。端末タイムゾーンが変わっても集計基準を変更しない。この方針は保存・CSV・復元へ影響するため実装前に承認する。

### 月間集計

- 総収入 = 対象月のincomeのamount合計。
- 総支出 = 対象月のexpenseのamount合計。
- 月間収支 = 総収入 − 総支出。
- カテゴリ別支出 = 対象月のexpenseをcategoryIdで分類した合計。

### 予算計算

- 使用額 = 月間総支出。
- 残額 = 月間予算 − 使用額。超過時は負数で表示する。
- 使用率 = 使用額 ÷ 月間予算 × 100。100%を超えて表示できる。
- 未設定は「予算未設定」とし、使用率を計算しない。

## 5 画面仕様

共通ナビゲーションは入力・履歴・集計・設定の4画面。iPadでは画面幅に応じた配置にする。読み込み中・空データ・保存中・失敗・成功を区別し、失敗時は再操作できる状態を保つ。

### Quick Entry

初期区分は支出。数字パッド、1桁削除、全消去、収支切替、カテゴリ、日付、任意メモ、保存を表示する。メモ以外はソフトウェアキーボードなしで操作できる。区分切替ではカテゴリ区分を一致させ、有効なカテゴリがない場合はカテゴリ作成を案内する。

保存中の連打を防ぎ、保存成功後に入力をリセットする。保存失敗時は入力値を維持して理由を表示する。「保存しました」は端末保存の成功を意味し、同期完了を意味しない。

### History

月移動、カテゴリフィルタ、日付降順の一覧、当月総支出を表示する。同時刻の順序はcreatedAt・idで安定させる案とする。行から編集を開き、既存のidとcreatedAtを保持して保存する。削除は内容を示した確認後に実行する。キャンセル時は変更しない。

### Analytics

選択月の収入・支出・収支、カテゴリ別支出の円グラフ、月別推移の棒グラフをSwift Chartsで表示する。月別推移は選択月までの12か月を提案する。取引のない月もゼロとして扱う。チャートと同じ値のテキストを提供し、色だけで区分を伝えない。

### Settings

カテゴリ管理、対象月の予算、iCloud案内、CSV出力、JSONバックアップ、JSON復元、アプリ情報を表示する。エクスポートと復元はOSのファイル選択・共有UIを使用する。復元プレビューからキャンセルできる。

### アクセシビリティ

タップ領域は最低44×44ptを提案する。数字パッドやアイコンへVoiceOverラベルを付ける。最大アクセシビリティ文字サイズでも保存や削除確認を操作でき、画面から必要な情報が欠落しない。横向き・iPad分割画面でも確認する。

## 6 RepositoryとUse Case

| 契約 | 操作 |
| --- | --- |
| TransactionRepository | save、find、月別取得、カテゴリ絞り込み、delete、全件取得 |
| CategoryRepository | 全件取得、区分別取得、save、並べ替え、アーカイブ |
| BudgetRepository | 年月別取得、save、全件取得 |
| BackupRepository | 一貫したスナップショット取得、検証済み復元の一括適用 |

Repositoryは失敗をthrowsで呼び出し側へ伝える。saveは同じ論理IDの更新または新規作成を行う。重複した論理IDを黙って任意の1件へ更新しない。複数Repositoryの順次saveで復元を実装しない。

| Use Case | 処理と結果 |
| --- | --- |
| CreateTransaction | 金額・カテゴリ検証、IDと日時生成、保存した値を返す |
| UpdateTransaction | 対象取得、検証、作成日時を維持し更新 |
| DeleteTransaction | UI確認後に指定IDを削除 |
| ManageCategory | 名称・区分検証、追加・更新・並べ替え・アーカイブ |
| SetMonthlyBudget | 年月・金額検証、対象月の予算を更新 |
| CalculateMonthlySummary | 対象月を抽出し整数で合計 |
| CalculateBudget | 使用額・残額・使用率を算出 |
| ExportBackup | スナップショットからCSVまたはJSONを生成 |
| PreviewImport | 全件検証、追加・更新・競合の件数を返す。保存しない |
| ImportBackup | 最新状態で再検証し、一括適用する |

金額不正、参照不正、重複、未対応スキーマ、ファイル読み込み失敗、保存失敗を区別する。利用者には対処可能な日本語を表示し、家計データやメモをログに出さない。

## 7 SwiftDataとCloudKit

全モデルの非Optional属性にデフォルトを設ける。@Attribute(.unique)に依存しない。カテゴリはUUIDで参照し、初期スキーマにはSwiftDataリレーションシップを設けない。将来追加する場合はOptional・逆参照・削除規則をレビューする。

ModelConfigurationのCloudKit Private Databaseを使用する。構成APIは[AppleのModelConfiguration仕様](https://developer.apple.com/documentation/swiftdata/modelconfiguration)に従う。Bundle ID、Team、CloudKit Container IDは開発者が決定し、実在する設定として扱うまで仮値を区別する。

XcodeでiCloud・CloudKit・Remote notificationsを設定する。SwiftDataによる同期に委ね、独自同期エンジンを実装しない。端末保存後は通信なしでも入力・履歴・集計を継続できる。iCloud設定案内に、未ログイン・容量不足・通信障害で同期が遅延する旨を表示する。

ModelContainer初期化失敗時はデータを削除しない。別の空ストアへ自動切替しない。起動エラーと再試行手段を表示し、復旧方法を開発者が調査できるようにする。iCloud未ログインとコンテナ初期化失敗を区別する。

クラウド上の同時編集・削除競合はAppleの同期挙動で検証する。updatedAtはアプリによる同期競合制御を保証するものではない。同期完了を測定していない状態で「同期済み」と表示しない。

スキーマの初版をVersionedSchemaとして記録する案とする。変更時はマイグレーション計画と既存ストアのテストを作成し、CloudKit本番スキーマの制約を確認する。本番データを壊す変更は禁止する。

## 8 バックアップと復元

### CSVの提案

UTF-8、ヘッダー付き、1取引1行。列はid、type、amount、categoryId、categoryName、occurredAt、memo、source、createdAt、updatedAt。日時はISO 8601、amountは桁区切りなしの整数とする。カンマ・引用符・改行を含む値は引用符で囲み、内部の引用符を二重化する。

表計算ソフトで式として解釈されるユーザー入力文字列には、出力時だけ先頭にアポストロフィを付ける案をレビューする。元データは変更しない。CSVは閲覧用であり完全復元には使わない。

### JSONの提案

トップレベルにschemaVersion、exportedAt、transactions、categories、budgetsを持つ。初版schemaVersionは1。UUIDは文字列、DateはUTCのISO 8601（小数秒を保持）、Int64はJSON整数とする。復元時はInt64として読み込み、浮動小数点や範囲外を拒否する。

未知のschemaVersionは拒否する。省略可能属性の扱いと将来バージョンの変換はスキーマごとに明記する。サンプル・テスト用データは架空の情報だけを使う。

### 復元プレビュー

1. ファイルを読み込み、形式とschemaVersionを検証する。
2. 全コレクションのUUID重複、属性、年月、参照カテゴリと区分を検証する。
3. 選択した復元方式で適用後の状態を構成し、整合性を検証する。
4. 現在のデータとの追加・更新・競合件数を表示する。
5. 利用者が方式と対象を確認した後、保存直前に再検証する。
6. 全件成功するか、失敗時に適用前のローカル状態を維持する。

提案としてファイル内部の欠落参照は既存データで補わず拒否する。バックアップは自己完結した状態を要求する。同じIDを異なるモデル種別に使うファイルも拒否する。

### 追加と上書きの提案

| 方式 | 新規ID | 既存ID | バックアップにない既存データ |
| --- | --- | --- | --- |
| 追加 | 追加 | 同一内容はスキップ、異なる内容は競合として適用を止める | 保持 |
| 上書き | 追加 | バックアップの内容で更新 | 保持 |

「上書き」は全件削除・全置換を意味しない。月間予算は別IDでも同じmonthKeyなら競合として提示する。カテゴリ上書きで既存取引の区分整合性が崩れる場合は拒否する。この方式は元仕様の曖昧さを具体化した提案であり、実装前に決定する。

適用は専用ModelContextでautosaveを無効にし、一度の保存にまとめる方式を検証する。検証・保存失敗時はrollbackして部分復元を防ぐ。ローカルの一括適用とCloudKitの他端末への同期は別であり、全端末同時の原子性を保証しない。同期到着でプレビュー後に状態が変わる場合は再プレビューを要求する。

既存データを更新する復元では事前JSONバックアップの作成を案内する。取消時は書き込みゼロ。負荷試験用の仮基準は10,000取引で、ファイルサイズ上限・応答時間・画面操作性を実測して決定する。

## 9 セキュリティと運用

独自認証・秘密鍵・外部解析・広告SDKを追加しない。家計データはSwiftDataと利用者のCloudKit Private Database、および利用者が選択したバックアップ先で扱う。バックアップは機密情報を含むため、共有・出力先を利用者に選択させる。アプリ独自のバックアップ暗号化は元仕様にないため、追加する場合は別途レビューする。

CloudKit Private Databaseをアプリ独自のエンドツーエンド暗号化と同一視しない。端末データやファイルのエラー診断で、金額・カテゴリ名・メモ・JSON全文をログに出さない。リリース用署名や本番スキーマ変更、配布は開発者の明示的承認後に行う。

Unit Testでは通常値に加え、Int64境界・集計オーバーフロー、閏年・月末、空一覧、予算超過、アーカイブカテゴリを確認する。同期テストには容量不足・一時障害・再インストール後の復元も含め、再インストールはバックアップ済みのテスト端末で行う。

各変更前に対象・理由・再利用・影響・リスク・手順・テスト方針を提示する。モデル、SwiftData、CloudKit、Repository、バックアップ・復元、重要なコアロジックを開発者レビュー対象とする。重要な設計判断はdocs/decisionsに記録する。

変更後は実装概要、変更ファイル、アーキテクチャ影響、セキュリティ、テスト結果、未解決事項、確認事項、次の作業を報告する。未実行のテストを成功扱いしない。レビューや実機確認が残る状態はMVP完成と報告しない。
